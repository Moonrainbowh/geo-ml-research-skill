# 实验账本

Pressure-test vocabulary note: project-specific terms are examples, not defaults; map them to the new project's terminology before use.

用于整理训练、baseline、HPO、消融、结果对比和失败实验。目标是把本地实验变成论文可用证据。

## 术语映射优先

本文件中的 `example_training_data.csv`、`task_configs.py`、6 任务、stage2 local search、GRU/BP/CNN、`keep_tuned` 等词是压测项目示例。新项目必须先映射为：

```text
main_data_file:
task_config_source:
task_completeness_unit:
model_families:
selection_rule:
followup_search_round:
primary_metric:
```

再套用可比性、split、provenance、HPO、selected config 和 claim-evidence 规则。不要把示例文件名、任务数、模型族或搜索轮次当成默认事实。

## 跨目录对比前置检查

跨目录、跨压缩包或跨机器结果对比时，先建立可比性，再算指标：

```text
Data file:
Row count:
Data hash:
Data provenance:
Generation script/source note:
Case/run/scenario ID availability:
Task config path:
Task names:
Train/val/test split:
Model purpose:
Run config:
Summary files:
```

必须检查：

- 主数据文件，例如项目中的 `example_training_data.csv`，样本数和哈希是否一致。
- 数据来源是否有一手证据：生成脚本、原始数据说明、上游导出记录、simulator/source 名称、抽样脚本。
- 是否存在显式 `case_id/run_id/scenario_id/project_id`；没有时不能把 row 当成独立工程或独立仿真组。
- 任务配置来源，例如当前压测项目中的 `task_configs.py`，其 task 顺序、阶段/任务计数、输入列、标签列是否一致。
- 训练/验证/测试划分逻辑是否一致；未确认时把泛化结论降级。
- 结果包用途：速度/可运行性测试、baseline、first-stage HPO、stage2 local search、论文主结果、备份包。

如果数据一致但划分策略未确认，可以比较模型表现，但必须写入风险。

## Data provenance gate

字段语义明确，不等于数据来源明确。写 Methods、Results 或审稿回复前，先把数据来源证据分级：

| provenance level | 需要证据 | 可写 | 不能写 |
|---|---|---|---|
| confirmed simulator/source | 生成脚本、原始导出说明、source 文件或可复现路径 | `generated by [source]`，并说明变量和抽样 | 把 provenance 证明当作 project/case/simulation-run/scenario 独立泛化证明 |
| named historical path only | `run_config.json` 或结果包中残留路径 | `archived results used data file at ...` | `the dataset was generated by [source]` |
| current CSV only | 只有 CSV、列名、task config | `numerical cavern-geometry forecasting dataset` | 命名 simulator、SSCLS、project/case/simulation-run/scenario 独立性 |
| external literature only | 只有相关论文或 simulator 论文 | 背景和工程动机 | 当前 CSV provenance |

必须检查：

- 当前机器上历史 source 路径是否存在；不存在时只能记为路径线索。
- 压缩包内是否保留上游数据或生成脚本；只包含 `example_training_data.csv` 时，不能反推出生成链。
- 阶段0/初始形态列是否可用于 group；若全常量或无唯一标识，不能作为 case id。
- 当前 task 是否真的使用所有列；未使用的全局参数不能写成模型输入。
- provenance 确认和 split 独立性必须分开：确认 source 只证明数据从哪里来，不证明 train/test 是 project/case/simulation-run/scenario 独立。

推荐 Methods 保守句：

```text
The dataset is treated as a numerical cavern-geometry forecasting dataset because the current CSV does not include an upstream generation record or explicit project/case/simulation-run/scenario identifiers.
```

## Split 审计硬规则

写实验账本、Results 或审稿回复前，先把 split unit 写清楚：

| split type | 能支持 | 不能支持 |
|---|---|---|
| row-level random split | 当前数据分布下的行级 holdout 表现 | project/case/simulation-run/scenario 级独立泛化或外部工程泛化 |
| group split / GroupKFold | 未见组跨 split 时的组级泛化 | 外部工程或新数据源泛化 |
| external validation | 外部数据上的验证 | 未覆盖工况之外的外推 |

必须检查：

- 是否有显式 `project_id`、`case_id`、`run_id`、`scenario_id`、`group` 或等价列。
- 代码是否使用 `GroupShuffleSplit`、`GroupKFold`、`groups=` 或手写组级划分。
- train/val/test 原始索引是否互斥。
- 全行 hash 或关键工程变量 hash 是否存在跨 split 重复。
- scaler、imputer、特征选择、PCA 等 preprocessing 是否只在 train 上 fit。
- 同一工程、同一仿真组、相邻阶段或同一时间序列窗口是否可能跨 train/test。

如果只有随机行级 split 且没有 group id，论文只能写 `row-level holdout` 或 `within-dataset evaluation`，不能写 `independent project/case/simulation-run/scenario-level generalization` 或 `external engineering generalization`。发现重复样本跨 train/test 时，必须在风险或 limitation 中写明；除非去重或 group split 复验通过，不能声称 `leakage-free`。

### Duplicate sensitivity levels

发现重复样本跨 split 后，先分清证据层级，不要把轻量检查写成重训结论：

| level | action | can support | cannot support |
|---|---|---|---|
| L0 metric-only | 在已有 prediction artifacts 中排除重复 test sample 后重算指标 | 该测试样本对已报告指标的影响大小 | 去重重训后的模型排序、split 独立性 |
| L1 minimal retrain | 去重或修正 split 后重训主模型/代表任务 | 主结论是否对最小去重重训敏感 | 全模型、全 HPO、投稿级最终证据 |
| L2 full rerun | 去重后重跑主模型、baseline、HPO、图表和锁文件 | 投稿级去重敏感性证据 | group-level 或 external validation，除非 split 单元也升级 |

## 多结果文件筛选

遇到多个 `summary.csv` 时，先做结果目录清单，不要直接合并：

| 类型 | 判断 | 处理 |
|---|---|---|
| 完整 6 任务 summary | 同一模型包含全部 task | 可进入主对比 |
| stage2 分任务 summary | 每个 task 一个 summary，run_config 标记 `stage2_local_search` | 先按 task 合并，再比较 |
| 单任务结果 | 只有 1 个 task | 只做补充，不进完整模型平均排名 |
| 备份/重复目录 | 路径含 backup、extract、tmp 或重复模型 | 用 `run_config.json`、时间、任务数判断是否保留 |
| 速度测试包 | README/runner 指向 GPU speed/usability | 与论文主结果分开解释 |

结果摘要中必须标明 artifact 路径，避免同名模型混淆。

## HPO 判断规则

- 不只看 tuned 是否最低。
- 必须检查 selected 结果，因为 tuned 可能回退到 baseline。
- `keep_tuned=True` 才说明调参结果被最终采用。
- 必须确认 `keep_tuned` / selected 决策基于 validation 指标，而不是 test 指标。
- 若代码或历史包用 `delta_test_*` 决定 `keep_tuned`，该 HPO 结果标为 test-selection 高风险，只能作为 exploratory，不可作为严格泛化证据。
- 如果 summary 同时有 `delta_val_*` 和 `delta_test_*`，用一行反向样本核查：当 test 改善但 val 变差时，`keep_tuned` 应为 False；否则可能仍在按 test 决策。
- 需要比较平均表现，也要指出单任务异常。
- 必须读取同级或上级 `run_config.json`，确认 `n_trials`、`trial_epochs`、`confirm_epochs`、`search_space`、`stage2_local_search` 和 `stage2_base_rule`。
- stage2/local-search 结果要和 first-stage 分开报告；二次搜索耗时更长不等于性能更好。
- 如果调参用到了测试集，必须标为高风险，不能写成可靠泛化。

HPO 输出至少包含：

```text
avg baseline RMSE:
avg tuned RMSE:
avg selected RMSE:
keep_tuned count:
selected vs baseline:
search time:
stage2 rule:
```

## Selected config lock

当实验存在 HPO、fallback、model selection、early stopping 或多候选模型时，除了结果包 manifest，还要单独锁定最终 selected 配置。目的不是展开所有 trial，而是防止把搜索候选误写成最终模型。

最小字段：

```text
Source package:
Task/model:
Selection rule:
Selection metric:
Selected source: baseline / tuned / checkpoint / candidate id
Selected config path or result file:
Selected hyperparameters:
Candidate/best hyperparameters:
Decision evidence:
Missing fields:
Field-name caveats:
```

硬规则：

- `best_params`、`best_trial`、best checkpoint 或 tuned candidate 只说明搜索过程；只有被 selection rule 保留后，才是最终 selected config。
- 当 selected 回退到 baseline 时，Methods 和 Supplementary table 必须写 baseline config，而不是写 best candidate config。
- selection rule 必须明确基于 train/validation/test 中哪一层证据；若 test 指标参与选择，结果只能标为 high-risk exploratory。
- 不从字段名反推架构语义。不同模型共用训练脚本时，`units`、`layers`、`hidden`、`gru_units` 等字段可能只是通用 override key，必须回到源码、模型注册表或配置类确认。
- 如果某个架构参数通过另一个配置字段复用传递，例如 `kernel_size` 存在于 HPO 参数但落到 `context_hidden_dim`，必须记录 source-code/config mapping；没有 mapping 证据时只标为 candidate/search field。
- 缺失字段写 `not recorded` 或 `not available in inspected artifacts`，不要用默认值补齐，除非默认值能从源码或配置文件直接证明。
- selected config lock 应和结果 summary、run_config、模型源码/注册表分开保存；结果好坏、搜索空间和最终配置是三类证据。

## Claim-evidence map

每个实验结论都写成：

```text
Claim:
Evidence:
Metric:
Artifact:
Boundary:
Status: supported / partial / weak / unsupported
```

例：

```text
Claim: GRU 在 6 个任务上整体比 BP/CNN 更稳。
Evidence: 6-task selected RMSE/R2 对比表。
Metric: avg selected RMSE, avg selected R2, per-task rank.
Artifact: outputs/.../summary.csv
Boundary: 仅限当前数据划分和任务定义。
Status: partial
```

## 岩土/ML 专项风险

- 数据泄漏：同一工程、同一阶段或相邻时间样本是否跨 train/test。
- split unit 不明：随机行级结果被误写成 project/case/simulation-run/scenario 级独立泛化。
- 重复样本泄漏：全行重复或关键工程变量重复跨 train/test。
- 外推：测试工况是否超出训练范围。
- 单位：半径、体积、深度、压力、时间阶段是否一致。
- 物理约束：结果是否违反非负、单调、几何或工程上限。
- HPO 污染：是否反复根据测试集调参。
- baseline 公平性：训练轮数、数据、特征、计算资源是否一致。
- 产物混淆：GPU 速度测试包、baseline 包、HPO 包和论文主结果包是否被混作同一证据。

## 失败实验处理

失败实验也要记录：

- 失败现象。
- 可能原因。
- 已排除原因。
- 是否影响论文结论。
- 后续是否需要复现。
