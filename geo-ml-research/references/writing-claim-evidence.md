# 写作与 Claim-Evidence

Pressure-test vocabulary note: project-specific terms are examples, not defaults; map them to the new project's terminology before use.

用于写岩土工程 + ML/DL 论文的摘要、引言、方法、实验、结果、讨论和结论。核心是先搭论证，再写句子。

## 术语映射优先

本文件中的盐穴、cavern geometry、SSCLS、GRU/BP/CNN、stage2、static baseline、radius/effective-radius 等词是当前压测项目示例。新项目必须先把这些角色映射为：

```text
engineering_object:
data_provenance_candidate:
model_family_or_comparator:
search_or_revision_round:
baseline_type:
engineering_output_metric:
```

再套用 claim-evidence、split、provenance、HPO 和写作规则。不要把示例项目的模型名、数据来源、任务数或工程变量继承为默认论文事实。

如果写作任务涉及盐穴/岩土 ML 论文的 Results 图文叙事、Figure caption、Figure 1/2 说明或用户要求学习领域论文风格，同时读取 `domain-figure-writing-style.md`，把模型指标连接回工程对象、阶段、几何参数和适用边界。

## 写作前论文契约

写正文前先整理：

```text
Paper type:
Engineering problem:
Main claim:
Data:
Model:
Baselines:
Metrics:
Key figures/tables:
Boundary:
Cannot claim:
Target venue:
```

如果 `Main claim`、`Data`、`Baselines`、`Metrics` 不清楚，不要直接写强 Results。

## Split 与泛化边界

写任何性能 claim 前，先把验证层级降到证据能支撑的最低层：

| evidence | 推荐表达 | 禁止表达 |
|---|---|---|
| 随机行级 split | `row-level holdout performance` / `within-dataset evaluation` | `independent project/case/simulation-run/scenario-level or external engineering generalization` |
| 组级 split | `group-level validation` | `external validation` |
| 外部数据 | `external validation on ...` | 覆盖所有未测试工况 |

如果没有显式 `project_id/case_id/run_id/scenario_id` 或等价 group 定义，不能把测试集写成独立项目、工程、仿真 run、scenario 或外部工程验证。若发现重复样本跨 train/test，Results 必须带边界句，并避免 `leakage-free`、`robustly`、`generalizes to unseen cases`。

可用边界句：

```text
All comparisons are based on the current random row-level holdout split and therefore should be interpreted as within-dataset performance rather than independent project-, case-, simulation-run-, scenario-level, or external engineering generalization.
```

## Data provenance 与 Methods 边界

写 Methods 的数据来源段前，先做 provenance gate。列名、字段语义、历史路径和外部 simulator 文献都不能单独证明当前 CSV 的来源。

| evidence | 推荐表达 | 禁止表达 |
|---|---|---|
| 只有当前 CSV + task config | `numerical cavern-geometry forecasting dataset` | `generated by SSCLS/[named simulator]` |
| 只有结果包历史路径，如 `path/to/example_training_data.csv` | `archived run_config paths indicate the data file used by the experiments` | `the dataset originated from that simulator/project` |
| 有 leaching/simulation 文献 | `provides engineering context for cavern-geometry variables` | `supports the provenance of our CSV` |
| 有生成脚本或原始导出说明 | 可命名 source，并说明变量、抽样和过滤 | 未说明的 project/case/simulation-run/scenario 独立性 |

如果没有生成脚本、原始数据说明或显式 `project_id/case_id/run_id/scenario_id`，Methods 只能把数据写成当前研究使用的数值 benchmark，不能写成命名 simulator 数据集或独立工程数据集。

即使后续 provenance 被确认，也只升级数据来源描述；独立泛化仍需单独证明，包括显式 group ID、group split 代码/日志和无跨组泄漏证据。

可用保守句：

```text
The experiments were conducted on the current numerical cavern-geometry forecasting dataset. Because the upstream data-generation record and explicit project/case/simulation-run/scenario identifiers are not available in the current CSV file, the dataset is treated as a row-level benchmark dataset rather than evidence of independent project-, case-, simulation-run-, scenario-level, or external engineering generalization.
```

如果后续 provenance 被确认，再升级为：

```text
The dataset was derived from [confirmed source], where [confirmed input variables] define the staged construction or geometric context and [confirmed output variables] represent the target cavern geometry.
```

Do not append an independent-generalization sentence unless group-level or external validation has been separately audited.

## Claim-evidence 表

```text
| claim | evidence | figure/table | strength | boundary |
|---|---|---|---|---|
```

强度：

- `strong`：同一任务、同一指标、直接比较支持。
- `partial`：只支持部分任务、部分工况或间接支持。
- `weak`：趋势存在但证据不足。
- `unsupported`：目前不能写成论文 claim。

## Section 结构

### Abstract

默认顺序：

`工程问题 -> 现有缺口 -> 方法/模型 -> 关键结果 -> 工程意义 -> 边界`

避免：

- “AI 技术发展迅速”式泛泛开头。
- 只说模型先进，不说工程问题。
- 没有数字或对照的强性能 claim。

### Introduction

默认顺序：

`工程场景 -> 预测/控制瓶颈 -> 传统方法限制 -> ML/DL 尝试及不足 -> 本文任务和贡献`

贡献必须绑定证据：

- 新数据或任务定义。
- 新模型或训练策略。
- 更公平/更系统的对照。
- 更清晰的工程边界或解释。

### Related Work

默认顺序：

`工程/机理背景 -> 直接邻近工作 -> 岩土/地下工程 ML 类比 -> 评估与泄漏风险 -> 本文定位`

Related Work 草稿必须从 reading cards 或已核验全文/摘要来源写，不直接从候选表标题生成。候选表只能决定“该读哪篇”，不能直接变成最终引用段落。

写作时可以先使用本地证据标记，例如 `[L003]`、`[L014]`，但必须在草稿开头说明这些是 reading-card markers，不是最终参考文献编号。等 BibTeX/DOI/页码核验完成后再转正式 citation。

直接邻近工作、类比工作和方法风险文献要分开：

- 直接邻近工作可支撑研究空白和任务定位。
- 类比工作只能支撑方法生态、指标写法或图表组织，不能支撑同任务性能。
- validation/leakage/HPO 文献只能支撑方法边界和 limitation，不能证明当前实验无泄漏。
- 摘要/出版页级卡只能写 `has been explored`、`reports`、`is a relevant neighboring study` 等弱支撑，不写强结论或完整实验细节。

### Methods

必须包含：

- 数据来源和预处理。
- 输入输出定义。
- 模型结构。
- 训练设置。
- baseline 和 HPO 策略。
- 评价指标。
- 复现所需环境或关键参数。

Methods 中的模型结构和 HPO 设置必须做 provenance gate：

- 模型结构句只从模型源码、模型注册表、配置类或已锁定的 architecture note 写，不从 summary 表的 `model_name` 反推细节。
- HPO 句只从 `run_config.json`、HPO 配置文件、trial 表或训练日志写；若最终包尚未锁定，只能写 family-level 描述，并把 exact hyperparameters 标为待补。
- 如果存在 baseline/tuned/selected/fallback 机制，必须先建立 selected config lock；`best_params`、best trial 或 tuned candidate 不等于最终模型配置。
- 当 selected 回退到 baseline 时，Methods 和 Supplementary table 写 baseline config；candidate config 只能写为 searched/tuned candidate。
- 只写已被 selected override、模型源码或配置类直接记录的字段。出现在 trial 表或 `best_params` 但未进入 selected override 的字段，只能写为 searched parameter，不写成 final selected hyperparameter。
- 若某个参数通过字段复用或适配层传递，例如一个字段在不同模型中代表不同架构含义，正文必须说明它是 source-code/config mapping，而不是 result summary 直接字段。
- stage2/local-search、速度测试包、单任务包和完整 6-task 主结果包必须分开描述，不能混成同一实验设置。
- 最终投稿前，Methods 应记录数据 hash、task config、split random state、模型源码、HPO run config、selected-rule 实现和图表 source data。

### Experiments / Results

默认证据阶梯：

`任务设置 -> baseline 对比 -> 主结果 -> HPO/消融 -> 误差分析 -> 工程边界`

每段只做一个主要 claim。结果段落先写可观察结果，再解释意义。

Results 硬规则：

- 没有具体数字、表号或图号时，只能写趋势句，不能写 `significant improvement`。
- 每个性能句至少绑定一个指标和一个对照来源。
- HPO 结果必须区分 `baseline`、`tuned`、`selected` 和 `keep_tuned`；只有 selected 或明确保留的 tuned 支持时，才写 HPO 改善。
- `keep_tuned` / selected 决策必须基于 validation 指标；如果来源包按 test 指标决定是否保留 tuned，只能写 exploratory result，不能写成严格测试集证据。
- 如果 `best_params` 与 selected config 不一致，Results 解释只能围绕 selected config 和 selected metric；不能用 unselected best candidate 来解释最终性能。
- stage2/local-search 若整体 RMSE 未提升，写成 `did not yield an overall RMSE improvement`；同时保留单任务或其他指标例外，不能简化成“stage2 更差”。
- 如果 `keep_tuned` 由 RMSE 决定，正文和图注必须说明主指标。RMSE 改善但 R2、MAE 或工程约束指标变差时，写成 mixed evidence，不能写 overall improvement。
- 工程误差段落必须说明用的是哪个变量和单位，例如 radius、effective radius、volume；不能把总 RMSE 直接翻译成工程可接受误差。
- 若 primary RMSE 和工程指标结论不一致，例如 stage2 selected RMSE 未整体提升但 effective-radius RMSE 略好，必须写成 secondary/mixed evidence。
- 如果缺少随机种子、方差或统计检验，不写 `significantly`、`robustly` 或 `consistently`，除非只描述“在当前设置下”。

HPO 句式模板：

```text
Under the selected-result rule, [Model A] improved over its baseline in [x/y] tasks, with `keep_tuned=True` indicating that the tuned configuration was retained for those tasks.
For [Model B], tuned performance deteriorated or remained inconsistent, so the selected results mainly reflect fallback to the baseline rather than a reliable HPO gain.
The stage2/local-search run did not yield an overall RMSE improvement; any task-level exception should be reported separately and not generalized to the full benchmark.
When RMSE and secondary metrics disagree, the evidence should be described as mixed rather than as an overall improvement.
If a result package used test-set deltas to decide `keep_tuned`, treat it as exploratory and exclude it from the main test-performance claim.
Engineering-error plots should translate model metrics into variable-specific error patterns, e.g. radius residuals or effective-radius RMSE, while preserving the row-level split boundary and any mismatch between primary and secondary metrics.
```

### Discussion

讨论：

- 为什么结果可能成立。
- 和现有方法关系。
- 工程适用范围。
- 失败工况或外推风险。
- 后续工作。

不要在 Discussion 里偷偷引入新实验结果。

## 中文 notes 到英文段落

流程：

1. 提取中文 notes 中的事实和 claim。
2. 删除口语、过程性抱怨和不确定猜测。
3. 补齐数据、指标、边界。
4. 先写英文 topic sentence。
5. 写证据句。
6. 写边界或含义句。
7. 中文说明做了哪些结构调整。

## 过度声称检查

看到以下词要谨慎：

- universally
- robustly
- significantly improves
- solves
- accurately predicts all
- generalizes to
- first
- novel

除非有跨数据、跨工况、统计检验和明确对照，否则改成更有边界的表达。

## 微措辞降级

有些句子不含明显强词，但仍会让审稿人追问证据强度。写投稿稿或 preflight 后修改主稿时，按下面规则收紧：

| 原表达风险 | 更稳表达 | 何时使用 |
|---|---|---|
| `negligible influence/effect` | `changed [metric] from A to B; did not materially change ... at the reported/displayed precision` | 没有预注册 materiality threshold，只能报告数值变化 |
| `useful gains` / `effective improvement` | `lower observed [metric] under the current split` | 只有固定 split、无 CI/多 seed/统计检验 |
| `establishes a benchmark` | `reports an internally audited evaluation` / `presents a bounded benchmark protocol` | 数据共享、provenance、外部验证或 public benchmark 条件未闭合 |
| `may explain why the model is better` | `one possible explanation/hypothesis is ...` | 没有消融、机制实验或额外验证 |
| `stage2 is better on secondary metric` | `secondary metric observation, not a reversal of the primary ranking` | 主指标和辅助指标方向不一致 |
| `further improves` | `is lower on [secondary metric] but does not improve [primary metric]` | stage2/local-search 或辅助指标与主指标不一致 |
| `validation-based selected rule` | `in the locked/inspected packages, decisions are consistent with validation-based rule` | 结果包来源复杂或存在旧 test-selection 路径 |

如果一个词既能表达事实也能表达价值判断，优先写事实和数字。例如写 `mean selected RMSE changed from A to B`，不要先写 `negligible`；写 `BP retained tuned settings in x/y tasks`，不要先写 `HPO was useful`。

在 preflight 或审稿体检输出中，`safe claim`、`executive verdict` 和 `claim-boundary audit` 不得把输入稿中的 `useful/negligible/further improves/establishes/deployment-ready` 原样带入，除非明确标成“原文风险措辞”。这些位置应直接给出降级后的推荐表达。对 duplicate sensitivity，默认写数值变化和 `metric-only` 边界，不写 `negligible`。
